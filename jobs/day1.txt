# Runtime notes (A100-80GB, from the H100 timings in the plan, section 6, doubled):
#  x1: about 280 gated held-out answer items (434 held-out ids x the 65 % answer gate rate measured on 1.7B).
#      Per item and layer: 3 finite arms (add at 2 alphas, replace) x 64 carriers, one shared clean forward per
#      frame, 2 linear JVPs and 1 far-gap JVP, everything x3 (none + shuffled + random). That is about 640 carrier
#      forwards and 70 chunked JVPs per item, i.e. 50-60 s on an A100 in fp32 (no TF32 override in the code), so
#      4-5 h per layer and about 6 h for L22, which also runs the answer frame. --resume makes a requeue cheap.
#  x3: 6 layers x 16 carriers x 6 greedy tokens per item. Answers (about 280 items, last position only): 1-1.5 h.
#      Bridges (about 150 gated items) scan every prompt position (mean about 14), so 6-7 h; it is the long pole
#      of the pack. If the queue is tight, drop x3_br to --layers 14,22,27.
#  x0: E7 on 14B is d = 5120, 40 blocks, 64 sampled output dims, 8 contexts of T = 128 (111 sources). Memory, not
#      time, is the constraint: --dim-batch 4 keeps the batched backward under about 55 GB with bf16 weights
#      (28 GB) and fp32 activations. About 6-7 h per layer; if it OOMs, halve --dim-batch (2) or --n-ctx-gap (4).
